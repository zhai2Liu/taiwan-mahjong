## 判斷

這個專案已有作為作品集的實質內容：完整台灣十六張遊戲、受資訊限制的電腦玩家、牌效分析、可靠存檔、局後檢討及已上線的決策題試讀。值得呈現的是「把領域規則轉成可驗證的產品，並持續處理真實操作問題」。

目前最大的不足是外部展示與個人貢獻證據：重要能力藏在階段文件中，作品第一眼仍像一般單人麻將；讀者難以快速知道你解決了什麼、你做了哪些判斷，以及 AI 協助到什麼程度。可以先放上履歷，但建議投遞前優先完成下面的 P0。

作品名稱建議：**青竹牌室｜台灣十六張麻將與決策練習**。介紹中說明「使用 AI 協作開發」，並區分開發工具和遊戲內 AI。不要只用「vibe coding 麻將遊戲」當整個專案的能力描述。

### P0：投遞前最值得補

| 缺口／本輪觀察 | 最小改善 | 完成判準 |
|---|---|---|

| **本人與 AI 的工作界線不明**。本輪 Git 作者統計為 81 筆 Codex 提交；不能以作者欄推定本人技術能力 | 加一節「我的角色與 AI 協作」；挑三個實際案例，逐一寫需求／判斷／AI 協助／驗收／修正；本人確認描述 | 每項個人貢獻都有可說明的決策或紀錄；不虛構手寫比例、審查經歷或技能熟練度 |

建議三個案例直接使用現有成果：

1. **不偷看暗牌的提示如何做到可信**：公開資訊相同，實際可胡結果可能不同；因此輸出「未知」而非猜成危險機率。連到 L1-A 反例及測試。
2. **如何避免遊戲進度與結算損壞**：成功動作、存檔、檢討紀錄的順序；儲存失敗與跨頁衝突；重載不可重複付款。連到實作及故障驗收。
3. **如何處理使用者提出的操作問題**：134 遇 2 的兩種吃法、雙擊出牌、中央海底、結算彈窗或台灣用詞。說明實際採用哪一例，附前後畫面與驗證；避免未量測就聲稱效率提升百分比。

個人貢獻建議採「產品需求與桌規取捨、試玩回報與驗收、AI 協作迭代」等可查證項目。若本人也能獨立解釋／修改程式，再具體補上相應模組；不要由 AI 代替本人宣稱已具備該能力。保留真實 Git 歷史，不為履歷改寫作者或製造假協作紀錄。

### P2：依職缺再投入

- **程式閱讀品質**：`style.css` 有大量單行壓縮樣式，`view.ts` 部分函式集中處理畫面。可以先做不改行為的排版和重複樣式整理，再依修改痛點拆解；檔案行數本身不是重寫理由。
- **測試報告可讀性**：現在沒有覆蓋率報告。可先用 Node 現有能力觀察重要分支，再決定是否有缺測；不追逐 100% 或新增大量鏡像測試。
- **日常維護**：依賴更新提醒、簡短 issue／PR 範本、英文摘要與分享預覽圖有幫助，但優先度低於作品介紹、本人案例及真實驗證。
- **文檔導航**：55 份 Markdown 多為有效的歷史證據。將作品入口、開發入口與歷史索引分開即可；不必搬動整個目錄、刪歷史或複製一套規格。

## 建議工作包及停止條件

| 順序 | 工作包 | 交付 | 結束條件 |
|---|---|---|---|
| W1 | 整理作品入口與角色 | 根目錄 README、一張架構圖、三個短案例、已上線／原型／研究狀態表 | 從陌生讀者角度能快速找 Demo、能力與證據；本人確認貢獻敘述 |

| W3 | 補可用性及驗證缺口 | 試讀離頁保護、PR 檢查、精選瀏覽器流程、具名裝置清單 | 三條核心展示路徑可靠，不損壞既有存檔，宣稱與測試範圍一致 |
| W4 | 實際試用與作品版本 | 少量真人觀察、至少一輪可追溯修正、Release 與履歷短述 | 能提出真實卡點、改動與結果；無資料時明寫待驗證 |

W1、W2 是目前投報效益最高的工作；W3 可先處理阻斷展示的問題，W4 需要真人參與。這些是可獨立完成的工作包，不估成固定工時或 token 配額，也不把無法取得的真人資料當成已完成。

若短片與既有試讀已能清楚展示，不新增專用展示模式。只有仍難以呈現核心決策時，才考慮一個完全隔離於正式存檔的固定情境；不直接公開會改寫存檔的測試 fixture。
